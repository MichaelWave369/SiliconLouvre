# Curatorial Publishing v1 · Exhibition 003

The Silicon Louvre now supports a public, human-reviewed **Community Gallery**. Its first iteration deliberately contains **no new approved artwork**. It is a real publishing path, not an automated approval machine.

## Authority boundary

A public GitHub issue or a downloadable creator kit is a **proposal**. It is **not** permission to exhibit an artwork. Publishing requires an identifiable human curator with repository merge authority to review original rights, collaborator consent, attribution accuracy and accessibility.

GitHub Actions validates the **structure** of approval records and rejects unreviewed entries, but cannot establish the truth of a creator's identity or ownership. An attacker with write permissions to `main` could falsify a JSON review receipt. Review receipts must therefore be cross-checked against source issues and the curator's actual approval on the GitHub pull request.

`.github/CODEOWNERS` requests review by `@MichaelWave369` for changes to the approved collection and artist directory. **Repository settings must enforce CODEOWNER review and protect `main`** for this to be a technical restriction. Merely committing CODEOWNERS does not protect a branch. Recommended settings: disallow direct pushes for nonauthorized accounts, require PRs, status checks, and code-owner review on protected `main`. Do not install auto-merge bots with catalog write permissions.

## From proposal to display

1. **Artist prepares the kit.** In the Creative Studio, fill the Exhibition Submission Desk with an artwork title, public alias, alt text, artistic process, contributor roles, and rights preferences. Export the portable `.json` kit and SVG, keeping local copies.
2. **Artist proposes for review.** The creator opens the public GitHub artist proposal form. Private consent or sensitive personal evidence must not be posted in public issue comments.
3. **Curator reviews independently.** Verify permission to reproduce or exhibit, collaborator attributions, the proposed rights and license terms, the source artwork's authenticity and integrity, and its accessibility/comfort. Record an auditable decision with only non-sensitive notes.
4. **Curator verifies kit.** Run `npm run inspect:submission -- path/to/kit.json`; this verifies the generated SVG matches the recipe. It does not confirm real-world rights.
5. **Curator stages an approved record.** Once rights and provenance have genuinely been checked, run:

   ```bash
   npm run stage:curated -- proposal.json https://github.com/MichaelWave369/SiliconLouvre/issues/101 2026-10-08 "Rights, credits, alt text and source art reviewed by human curator." --ack-human-review
   ```

   The command prints an example catalog record. It **does not modify repository files, open a PR, publish art, or verify the curator's identity**. Replace the example issue URL and notes with the actual reviewed evidence.

6. **Open an approval PR.** Add the record to `curatedWorks` in `src/data/curatedWorks.js` using a unique ID. Include the proposal issue URL and curator decision record. Review all publicly visible words; do not paste sensitive information.
7. **Run release validation.** `npm run verify:curated` checks approval status, references, source recipe, valid creative credits, license category and review receipt. `npm run check` also runs all museum tests, founding-image integrity checks and production build.
8. **Human approves and merges.** Confirm the decision in a PR review, ensure green checks, and merge through GitHub's protected branch rules. GitHub Pages then renders the work using the same deterministic SVG generator as the original creator kit, avoiding third-party remote image uploads and active SVG content.

## What is published?

Exhibition 003 displays only data in the curated collection catalog. A work receives:

- A title and the creator's chosen public artist/studio name.
- An exact, reproducible static 800 × 800 SVG generated from its approved recipe.
- A museum plaque with artwork story, creative process, credited human/AI contributions, and stated rights status.
- The reviewer's GitHub handle and approval date plus non-sensitive decision notes.
- A link to the source proposal issue, when appropriate.

The initial exhibit catalog is empty: no applicant or AI agent receives automatic artist status, and a public proposal never appears in the collection unless its approved metadata is intentionally merged.

## Technical contract

`src/data/curatedWorks.js` holds the records and Exhibition 003 metadata.

`src/lib/curation.js` enforces approved-work schemas; `scripts/verify-curated.mjs` integrates this gate into CI; `scripts/stage-curated.mjs` prepares text for an optional human-authored PR.

The catalog intentionally stores **SVG recipes**, not submitted arbitrary SVG markup. Artwork presentation is generated by the museum's fixed, allowlisted vector generator. The `src/CommunityGallery.jsx` viewer uses a browser image element with text credit fields in React, not `dangerouslySetInnerHTML`.

For artwork **not created with the museum's Creative Studio**, use the existing artist proposal form and develop a separate, properly reviewed asset pipeline. This version does not accept arbitrary uploaded image files into the approved public catalog.

## Curatorial caveats

- `rights-retained` means the artist retains rights and any license to show the work must be separately documented. Displaying that status is not itself proof of permission.
- Proposed CC BY/CC0 options likewise require verification of actual authorization. Do not assume a checkbox is a license grant.
- A source issue may be public; keep sensitive evidence in an authorized private process.
- A visitor's private creative drafts remain private to their browser, never automatically harvested for publication.
- The GitHub reviewer identity listed in a record is **documentary metadata**, not proof of a signed review unless corroborated by GitHub's actual PR approval and protected branch.
- Curator-controlled withdrawal, revision history, and artist takedown procedures should be documented when first external artwork is published.
- The original six Founding Masters image files are a separate pending installation, tracked in Issue #7.
